# GitHub sandbox port

This draft targets `jacob-vincent-mink/omarchy-github:main`, not the original repository. It depends on [the independent Rust sandbox runtime](https://github.com/jacob-vincent-mink/omarchy/pull/3).

## Plugin changes

`manifest.json` adds sandbox requests for fourteen exact own-settings read/write keys, browser/webapp links, and eleven selectable `/usr/bin/gh` command-tree leaves. The tree spells out the original helper's sign-in check, REST endpoints, exact GraphQL documents and bounded variables. The two notification-write leaves are separately selectable from reads.

`omarchy-github-fetch` selects the literal argv prefix `/bootstrap --exec gh` when running in the worker, including its parallel Actions jobs. Standalone execution still calls `gh` directly. A declined sign-in selection produces an actionable message. This snapshot check is for feedback only; the broker owns authorization. There is no `gh` shim, PATH override, replacement API client or plugin-specific Rust provider. The original queries, pagination, aggregation, filters and notification-boundary logic remain in the original helper. Plugin QML is unchanged.

The manifest requests access; user selection approves an exact revision, executable digest and command leaves. The worker has neither real credentials nor direct network access. Approved host-side `gh` jobs use the user's normal CLI authentication and network access. Exec is delegated host authority: argument matching does not sandbox the CLI's application semantics, dependencies, configuration or delegated effects. A future CLI byte change requires reapproval.

## Evidence

The original helper, panel-source and service-source test suites pass. A private integration experiment ran this helper in the actual worker and the installed `gh` in supervised host jobs, with fake credentials, an account-free local API and an empty Internet namespace. Three ten-case runs passed after adopting direct bootstrap calls: ordinary access, read-only selection and declined sign-in. These exercise repository/notification/Actions pagination, filters, authored PR rollups, scan modes and limits, single/bulk writes and rejected extra authority. Read-only selection produced no API writes; declined sign-in produced no API calls. The earlier logged-out, partial-error and rate-limit helper matrix used the since-removed forwarding shim; current-port graphical error checks are recorded below.

Private-display preparation also rendered the original dashboard with fixture data and exercised original settings controls. The current fourteen-key settings contract passed a complete six-control save/reopen/full-host-restart trial on 2026-09-09. A second run selected only reads: attempted edits visibly rolled back, the bounded notice named the unwritable setting, and unchanged defaults survived restart. The original QML and manifest were copied byte-for-byte, real pointer/keyboard input operated the controls, and the original shell writer preserved unselected settings and unrelated configuration. Saved, reopened, restored and declined render states were inspected. All settings-helper and IPC routes pointed to a disposable host; no live settings or real inbox state was changed. These experiments do not claim real-account or full original-panel acceptance.

Separate current-port graphical trials ran the unchanged panel/service/helper and installed `gh` with only six selected read/sign-in leaves, fake credentials and a Unix-only API inside an empty Internet namespace. Rejected authentication rendered the original sign-in guidance and made no dashboard API calls. A notifications HTTP 403 rendered the partial-results notice while retaining the successful repository and its metrics. Zero remaining GraphQL requests rendered the original rate-limit warning and retained the repository. Both normal startup and panel-open refreshes finished before inspecting the latter captures. These are focused error-state checks with Actions scanning off, not a rerun of the earlier ten-case helper matrix or a real-account test. The original files were copied byte-for-byte; all configuration and API records were disposable, and no write leaves were selected.

Private repository UI trials then exercised all filter buttons and sort choices with twelve API-sourced repositories and a ten-row render cap. Search reached a repository beyond that cap; search/Escape, `j`/`k`, arrows, pointer departure with retained keyboard focus, clicks and Enter/Space activation passed. Both browser-tab and web-app modes delivered the exact expected URLs through the actual URL broker and fixed helper to private launch recorders and closed the panel. No real browser opened. Captures verify the issue/PR/star subsets and ordering; Actions scanning was off, so that filter/sort covers only empty results and zero-count ties. The original QML remained unchanged.

Original bulk-confirmation UI trials verified first-click arming without writes, expiry, close/reopen reset and exact captured-boundary mutations against a disposable inbox. An unseen same-second arrival survived and remained visible. Declined write leaves caused zero API mutations and restored all original rows; a rejected final boundary PATCH preserved the earlier successful writes and refreshed to the actual remaining unread rows. Armed, expired, reopened and settled recovery captures were inspected; the transient action-error text still needs a timed capture. No real inbox or live grants were changed.

Later timed captures verified both bulk error notices before expiry. Individual-notification trials also pass: `m`, the checkmark and row-open each issue exactly one PATCH for the selected thread and retain the two other unread rows. Row-open sends the exact issue URL through the real URL broker/helper to a private web-app recorder, closes the panel and preserves the result after reopening. Declining the write leaf makes no API mutation; a rejected PATCH restores the row. Their transient error notices and refreshed results were visually inspected. The current denial message uses Rust's raw error formatting; this is behavior coverage, not polished wording.

These tests found a runtime input bug: synchronous executable verification could delay key release enough for one short `m` tap to mark multiple threads. Ward now prepares executable snapshots outside the input loop and rechecks authority before launch, without changing keyboard-repeat semantics. Both 21 ms and 172 ms taps and all five individual success/denial/failure paths passed with the asynchronous implementation. Plugin QML and the helper remained unchanged, and all API traffic used fake credentials with Internet access disabled. That runtime fix is not yet deployed to the active desktop.
